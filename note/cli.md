## typer 
你用类型标注声明函数，它把函数自动"翻译"成一个完整的命令行程序。除了生成 --help 和校验，它还会做：
1. 类型解析与强制转换：priority: int 会帮你把字符串参数转成 int，转不了就给出规范的错误和退出码，而不是抛出一堆 traceback。
2. 必填/可选声明：title: str（无默认值 = 必填参数）、priority: int = 1（有默认值 = --option），一套规则全覆盖。
3. 子命令组织：Typer() + @app.command() 天然对应"程序 → 子命令"的层级（agent-study tasks add），不用自己搭解析树。
4. shell 自动补全：一条命令就能生成 Bash/Zsh/Fish 补全脚本，命令多了很有价值。
5. 输出/交互增强：彩色输出、进度条、确认提示（typer.confirm）等开箱即用。
6. 可测试性：CliRunner 配合 pytest。
7. 它底层基于 Click，只是把 Click 的"装饰器 + 手写类型"换成了"读 Python 类型标注"。

## CLI 对 AI 工程项目有什么价值

一句话：**在 AI 工程里，CLI 是 Agent 的"手"——它把一个模型/脚本变成一件可以被稳定调用的工具。**

AI 工程项目和普通后端最大的区别之一，是它大量产出"非 HTTP 的能力单元"：调一次模型 API、跑一次检索、写一次向量库、评估一批数据集、导出一份报告。这些东西在早期都长成脚本形态。脚本只能人手敲，Agent 调不了，CI 复用不了，线上也排障不了。CLI 是把它们从"一次性代码"升级成"可复用工具"的最低成本一步。

### 1. 一份进程级的工具契约

Agent 要动手，就得有个**契约明确**的外部接口。CLI 的参数、退出码、stdout/stderr 天然就是一份机器可读的契约——Agent 不需要理解你的 Python 类，只需要会解析命令行。

相比"在 Agent 进程里 import 你的函数"，进程级调用还有两个实在的好处：

- **隔离**：Agent 主进程不会因为工具崩了而带崩；工具的全局状态、env 污染、依赖冲突都被隔在子进程外。
- **权限可控**：要限制 Agent 只能做某几件事，限制"允许执行的命令"比限制"允许调用的函数"容易得多——白名单式授权是命令级的。

### 2. 默认无副作用：AI 工程特有的风险控制

在 AI 工程里，"调用"经常等于"花钱"。一次 LLM 调用、一次 embedding 批处理、一次带 --retries 的重试，都是真实账单。所以 CLI 的默认行为必须是**保守的**：

| 默认行为 | 理由 |
| --- | --- |
| 不带参数 → 打印帮助并退出 | 误触发的成本是 0 |
| `--help` 不产生任何副作用 | 帮助是最常被调用的命令，它必须绝对干净 |
| 联网命令必须显式调用 | 防止"跑一下看看"直接打爆配额 |
| 危险操作要显式 flag，不设"默认开" | 默认值应该是安全的那一侧 |

本项目里这条被做成了硬约束，并且用测试钉住：

- `agent_study/__main__.py` 不再默认跑整套演示，也不再默认发网络请求；
- `agent_study/cli.py` 里所有联网模块（`httpx`、`urllib.request`）都是**函数内延迟导入**——`import agent_study.cli` 之后 `sys.modules` 里根本没有 `httpx`；
- 测试里用 socket 守卫（把 `socket.connect` 换成抛异常的桩）验证：跑 `--help` / `demo` / `tasks` 时任何一次外发连接都会让测试失败。

对 Agent 尤其重要：Agent 判断失误多发一轮批量调用，账单直接爆；CLI 的"默认不做事"就是最外层的一道保险。

### 3. 退出码和 stdout 是编排契约

CLI 之所以能被 shell、CI、Agent 编排，靠的是两个约定俗成的东西：

- **退出码**：`0` 成功、非 `0` 失败。CI 的 `&&` / `||`、Agent 的"这次调用算不算成功"都靠它。
- **stdout 给人看的数据，stderr 给诊断信息**：Agent 可以放心解析 stdout，把 stderr 当日志。

本项目里 `github async` 就是这个模式：多个用户并发拉取，其中一个 404 了，不中断其他请求，但整体退出码为 `1`，并在 stderr 里标记 `ghost: FAILED`——**部分失败既不吞掉、也不掩盖成成功**。这是 Agent 判断"要不要重试"的依据。

### 4. 人和 Agent 共用同一个入口

如果 Agent 走一套私有接口、人走另一套接口，就会出现"Agent 报的错人复现不了"。共用 CLI 就没有这个问题：Agent 执行的那条命令，人可以原样敲一遍；人手动验证过的那条命令，Agent 也能用。

这在调试 Agent 时尤其值钱——你能直接看 Agent 到底调了什么、参数是什么、输出是什么，而不是去翻一屏结构不明的日志。

### 5. 线上排障入口

线上出问题时，工程师需要一个**能在服务器上直接敲**的命令去复现问题，而不是临时写个脚本、删掉、再删掉。

本项目的 `config` 命令就是干这个的：脱敏打印当前生效的配置（`MODEL_NAME` / `API_BASE_URL` / 掩码后的 `API_KEY`）。"线上到底加载了哪个 .env、用的什么 base_url"这类问题，一条命令解决，不用进 Python 解释器。

`tasks` 子命令同理——状态文件可读可写，运维动作不需要写代码。

### 6. 天然的测试接缝

CLI 把"参数解析"和"业务逻辑"隔开，中间那层就是测试接缝：

- 用 `CliRunner` 驱动，**参数解析、退出码、stdout、stderr 全部可断言**；
- 退出码 + stdout 的组合就是一份**契约**，改坏了测试会红；
- 副作用（文件、网络）都在命令内部，测试里换成临时目录和桩即可。

本项目 30 个 CLI 测试就是靠这个跑起来的：同步命令在 `get_github_user` 边界打桩，异步命令用 `respx` 打桩 httpx，**整个测试套件不依赖外网可达**。

### 7. 把资源边界显式化

AI 工程的成本和稳定性，八成由几个边界参数决定：并发数、重试次数、最大步数、token 上限、超时。

把这些做成 CLI 参数，等于把"边界"从代码里搬到了调用面上——人和 Agent 都能施加约束，而不是只能改代码：

- `github async --retries 1` —— 限流时退避重试；
- `AsyncGitHubClient(max_retries=...)` —— 只对幂等方法重试，非幂等写接口拒绝重试；
- `AgentInput.max_steps: int = Field(ge=1, le=50)` —— 步数上限写进类型约束，非法值在入口就被拒。

### 8. 从 demo 到产品的最低成本一步

很多 AI 工程项目的第一版就是个 demo 脚本。把它变成别人能用的东西，通常的路径是：写 HTTP 服务 → 做前端 → 做鉴权 → 做部署。这一条链路很长。

CLI 的中间态便宜得多：**不用常驻服务、不用做前端、不用设计 REST 规范，就能让别人（和 Agent）用起来**。等到确实需要多用户、远程调用、权限体系时，再把底下的逻辑抽成库，CLI 退化成 SDK 的一层薄封装——因为 CLI 本身就已经强制你把逻辑和入口分开了。

| --- | --- |
| `agent-study --help` | 默认无副作用；入口自描述 |

## CLI 不适合做什么

别把 CLI 当银弹，它有明确的边界：

- **不是用户产品接口**：面向终端消费者的产品还是需要 API 或 Web UI，CLI 面向的是开发者和 Agent。
- **不在每次请求的链路上**：进程启动开销远大于函数调用，CLI 是编排层，不是热路径。
- **不替代可观测性**：结构化日志、metrics、trace 仍然要单独做（本项目有 `logging_config.py`）。
- **不替代服务治理**：多租户、鉴权、配额、灰度，这些是服务层的事。

## 几条可复用的设计原则

1. **默认无副作用**——不带参数只显示帮助；联网/付费操作必须显式。
2. **导入无副作用**——重量级和联网模块延迟导入到函数内部。
3. **退出码即契约**——成功 0、失败非 0；部分失败要如实反映。
4. **stdout 与 stderr 分工**——stdout 是数据，stderr 是诊断。
5. **一个子命令一件事**——子命令之间不共享状态，各自可独立测试。
6. **业务逻辑不写在 CLI 里**——CLI 只做参数解析与调度，逻辑下沉到模块，CLI 保持薄。
7. **路径要锚定，不能依赖 CWD**——写文件、读配置一律用绝对路径（`Path(__file__).resolve().parent` 或用户数据目录），否则同一个命令在项目根跑和在别处跑会读写到不同的文件。
8. **写操作要落在工作区之外**——默认写到用户数据目录（`~/.agent-study/`）或临时目录，不要默认写进被 git 跟踪的项目文件，否则跑一次演示就脏一次工作区。
9. **输入要在入口就校验**——空标题、纯空白这类垃圾数据应该在入口被拒掉（退出码非 0），而不是写进存储之后再由下游发现。

### 关于第 7、8 条的实战例子

重构前这个项目的任务文件写死成 `Path("agent_study") / "task.txt"`——相对路径，依赖当前工作目录；而且 `agent_study/task.txt` 是被 git 跟踪的，`demo` 每跑一次就往里追加一行 `adhoc task`，工作区永远是脏的。

改法：

```python
PACKAGE_DIR = Path(__file__).resolve().parent
PROJECT_ROOT = PACKAGE_DIR.parent
USER_DATA_DIR = Path.home() / ".agent-study"
DEFAULT_TASK_FILE = USER_DATA_DIR / "tasks.txt"   # 与 CWD 无关，也在 git 工作区之外
```

`demo` 更进一步，用 `tempfile.TemporaryDirectory()` 起一个临时目录，退出时自动清理——演示数据不落盘，更不碰用户自己的任务清单。

这类问题的共同点是：**CLI 的默认行为会变成用户工作区的一部分**。默认值不是"随便挑一个"，它会被用户继承、被 CI 继承、被 Agent 继承。

## 面试问题

问题：为什么给 AI Agent 做工具，优先做 CLI 而不是 HTTP API？

1. **实现成本**：CLI 不需要常驻服务、不需要鉴权体系、不需要前端，一两天能出可用版本；HTTP API 还要考虑部署、版本、权限。
2. **进程隔离**：Agent 调用 CLI 走的是子进程，工具崩了不影响 Agent 主进程，工具的依赖冲突和全局状态也隔离开。对比 import 库函数，Agent 沙箱里跑一段不受控代码的风险高得多。
3. **授权粒度**：白名单"允许执行哪几条命令"比白名单"允许调用哪些函数"更容易做，也更容易审计。
4. **组合性**：CLI 天然能被 shell 管道、CI 步骤、Agent 的工具调用复用，一份实现多处用。
5. **可观测**：命令行本身就是一条完整的事件记录——参数、退出码、stdout、stderr 都在，比调一个接口再翻日志更容易复盘。

追问：那什么时候还是应该做 HTTP API？
当需要多用户并发访问、跨机器调用、需要鉴权与配额、需要被第三方系统集成时，HTTP API 才是对的。CLI 和 API 不是二选一：把业务逻辑放在库里，CLI 和 API 都是它的一层薄封装，先 CLI 后 API 往往是最稳的演进路径。
