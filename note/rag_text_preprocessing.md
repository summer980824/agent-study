# 为什么文本预处理会影响 RAG 的质量？

RAG 的链路是：文档 → **预处理** → 分块（chunking）→ 向量化（embedding）→ 检索（retrieval）→ 拼进 Prompt → 生成。预处理是这条链的第一环，它的输出直接决定后面每一步的输入质量。"垃圾进，垃圾出"在这里体现得尤为明显。

## 1. 预处理决定 embedding 的质量

检索的核心是**语义向量相似度**，而向量是 chunk 文本经过 embedding 模型得到的。embedding 模型对输入文本的表面形式非常敏感：

- **Unicode 表示不一致**：`café`（NFC，单码点）和 `cafe\u0301`（NFD，e + 组合重音）语义完全相同，但 BPE 分词器会把它们切成不同的 token 序列，产生不同的向量。同一个词在文档库里两种写法混杂，检索时相似度就会被稀释。
- **控制字符和零宽字符**：`\x00`、`\x07`、BOM、零宽空格等不可见字符会变成无意义的 token，污染向量表示，也可能让下游的 Markdown/HTML 解析器行为异常。
- **多余空白**：连续空格、tab、不换行空格（`\xa0`）白白消耗 token（embedding 模型通常有 512/8192 token 的输入上限），还会让"看起来一样"的两段文本向量不一致。

→ 这正是 `normalize_text()` 做 NFC 归一、`clean_text()` 清控制字符和折叠空白的原因。

## 2. 预处理决定分块的边界质量

分块几乎都依赖**段落边界**（空行），而边界切错是 RAG 质量的头号杀手：

- 换行符不统一（`\r\n`、`\r` 混用）会让按 `\n\n` 找空行的分块器失灵，把本属于同一段落的句子切到两个 chunk 里——检索到一半上下文，LLM 只能基于残句回答。
- 冗余空行会产生空 chunk 或把相邻段落错误合并：合并则一个 chunk 混入多个主题，向量被"平均化"，检索精度下降；空 chunk 则浪费 top-k 的宝贵名额。
- 不过滤空段落，检索时可能把"无信息片段"排在前面，挤掉真正相关的文档。

→ 对应 `normalize_text()` 的换行统一和 `split_text()` 的边界拆分与空段落过滤。

## 3. 噪声会沿着链路放大

预处理的问题不会在原地停止，而是逐级放大：

1. 噪声文本 → embedding 偏移 → 相似度排名错误
2. 分块边界错误 → chunk 语义不完整 → 检索回来的上下文答非所问
3. 脏上下文进入 Prompt → LLM 基于残缺/矛盾的上下文生成 → 幻觉

反过来，干净的预处理还能带来**确定性和一致性**：同一文档多次处理得到相同结果，有利于去重、缓存 embedding、增量索引更新。

## 4. 总结

| 预处理操作 | 影响的环节 | 后果 |
| --- | --- | --- |
| Unicode 归一（NFC） | 分词、embedding | 同义文本向量一致，匹配稳定 |
| 换行符统一 | 分块 | 段落边界正确，chunk 语义完整 |
| 控制字符清理 | embedding、解析 | 向量不被噪声稀释 |
| 空白折叠 | token 效率、embedding | 省 token，表达紧凑 |
| 段落拆分 + 空段落过滤 | 分块、检索 | top-k 名额不浪费，检索精度高 |

一句话：**预处理不是可有可无的清洗步骤，而是决定了"被向量化的是什么、被切分的是哪些语义单元"——这两个要素正是 RAG 检索质量的根基。**
