## 测试观察
1. 英文效率最高：常见英文单词整个是一个 token，平均 5~6 个字符才 1 个 token(0.18 字符比，即每字符约 0.18 token)。
2. 中文 密度高：几乎每个汉字单独占一个 token,20 个字符切出 15 个 token（每字符 0.75 token)。这是 cl100k_base 对 CJK 的特点——字越多 token 越接近 1:。
3. 代码和 JSON 居中：缩进、标点、键名都会被切分，每字符约 0.38 token。

## 面试问答

### Q: Token 和字符有什么区别？

字符（character）是文本的存储单位：一个英文字母、一个汉字、一个空格都算 1 个字符，Python 里 `len(text)` 数的就是它。字符数只跟"写了多少个符号"有关，跟语义无关。

Token 是模型处理文本的计算单位：分词器（tokenizer）把字符串切成模型词表里的条目，模型的一切开销——上下文窗口、计费、生成速度——都按 token 计。

两者不是固定换算关系（实测 o200k_base 编码）：

| 文本类型 | 字符数 | token 数 | 每字符 token |
|---|---|---|---|
| 英文句子 | 45 | 8 | 0.18 |
| 中文句子 | 20 | 10 | 0.50 |
| Python 代码 | 32 | 12 | 0.38 |
| JSON | 37 | 14 | 0.38 |

规律：英文常见单词整个是一个 token，最省；中文在 o200k 里约 2 字符 1 token（旧的 cl100k 接近 1 字 1 token）；代码和 JSON 的标点、缩进会被切碎，居中。

所以"这段文字多少 token"不能只数字符数再乘固定比例，必须用对应模型的编码实测（本项目用 `count_tokens(text, encoding_name)`）。

### Q: 上下文窗口限制什么？

上下文窗口是模型一次能"看到"的 token 总数上限，输入和输出**共享**这个预算。128K 窗口意味着：system prompt + 历史对话 + 用户输入 + 模型回复，加起来不能超过 128K token；超出的部分不会报错，而是被静默截断——最早的消息直接丢失，模型"忘记"前面的内容。

它还间接限制了：单次回复的最大长度（max_tokens 是从同一预算里预留给输出的）、多轮对话能记住多远、RAG 一次能塞进多少文档。注意窗口按 token 而非字符计，塞中文比塞英文更快占满窗口。

### Q: 估算一段长文本占 GPT-4o 128K 上下文窗口的百分比

分三步：

1. **确定容量**:128K = 131,072 token。
2. **用对编码**:GPT-4o 用的是 `o200k_base`，不是 `cl100k_base`（后者是 GPT-4/3.5 时代的）。本项目 `count_tokens(text, "o200k_base")` 即可。
3. **算出占比**:`占比 = count_tokens(text, "o200k_base") / 131072 × 100%`。

没有现成分词器时的速算：按上面的实测，英文约 0.18 token/字符，中文约 0.50，代码/JSON 约 0.38。换算成容量直觉：

- 纯英文长文：128K 窗口约容纳 73 万字符；
- 纯中文长文：约容纳 26 万字符；
- 代码/JSON：约容纳 35 万字符。

举例：一篇 5 万字符的纯英文文档 ≈ 5万 × 0.18 ≈ 9,000 token，约占 128K 窗口的 7%；同样 5 万字符的中文文档 ≈ 25,000 token，约占 19%。混合文本按段落类型加权估计，有分词器就直接实测。


## tiktoken 的用途

tiktoken 是 OpenAI 的开源分词器库（BPE 算法），本地运行、无需联网，核心作用是**在调用 API 之前就能精确知道一段文本会被切成多少 token**。典型用途：

1. **费用预估**：API 按 token 计费。发请求前用 `count_tokens` 算出 prompt token 数，乘以单价即可预估成本，避免"跑完才发现烧了几美元"。

2. **上下文窗口管理**：多轮对话累积前，先算历史消息 + system prompt + 新输入的总 token 数；接近上限时主动截断或摘要最早的消息，而不是等模型静默遗忘。要预留 `max_tokens` 给回复——它是从同一预算里扣的。

3. **RAG 文档切块（chunking）**：向量化前按 token 数切分文档（而不是按字符数），保证每块不超嵌入模型的输入上限，也避免句子被从中间切断。

4. **输入超长拦截**：用户粘贴一大段文本时，先测 token 数，超预算就拒绝或提示精简，省一次注定失败的请求。

5. **观察分词行为**：`encoding.encode(text)` 返回 token id 列表，`encoding.decode([id])` 可以反查每个 token 对应的原文片段，用于理解模型"看到"的到底是什么（比如为什么中文比英文费 token）。

**注意事项**：

- 编码必须和模型匹配：GPT-4o 用 `o200k_base`,GPT-4/3.5 用 `cl100k_base`，选错结果差很多（中文可差一倍）。
- 聊天消息要带上角色和格式开销：实际发送的是 `{"role": ..., "content": ...}` 序列化后的文本，token 数比裸 content 略多，精确场景可用 `tiktoken` 官方提供的聊天模板函数。

本项目的 `agent_study/token_count.py` 就是对 tiktoken 的薄封装（空文本直接返回 0，避免无意义的编码调用）。
