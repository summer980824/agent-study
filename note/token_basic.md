## 实验结果

四段样本文本，分别用两种编码器实测（`agent_study/token_count_demo.py` 可复跑）。**不同编码器的数字不能直接对比，引用时必须注明用的是哪个。**

样本：
1. 英文：`Large language models process text as tokens.`
2. 中文：`大型语言模型会将文本转换成 Token。`
3. 代码：`def add(a, b):\n    return a + b\n`
4. JSON：`{"user_id": 1001, "status": "active"}`

### cl100k_base（GPT-4 / GPT-3.5 时代，本项目 `count_tokens` 默认值）

| 文本类型 | 字符数 | token 数 | 每字符 token |
|---|---|---|---|
| 英文句子 | 45 | 8 | 0.1778 |
| 中文句子 | 20 | 15 | 0.75 |
| Python 代码 | 32 | 12 | 0.375 |
| JSON | 37 | 14 | 0.3784 |

### o200k_base（GPT-4o / o1 系列）

| 文本类型 | 字符数 | token 数 | 每字符 token |
|---|---|---|---|
| 英文句子 | 45 | 8 | 0.1778 |
| 中文句子 | 20 | 10 | 0.50 |
| Python 代码 | 32 | 12 | 0.375 |
| JSON | 37 | 14 | 0.3784 |

观察：
1. 英文效率最高：常见英文单词整个是一个 token，平均 5~6 个字符才 1 个 token。
2. 中文密度高，且对编码器敏感：cl100k 几乎 1 字 1 token，o200k 约 2 字符 1 token——两者相差近一倍，统计中文文本时选错编码器误差最大。
3. 代码和 JSON 居中：缩进、标点、键名都会被切分，两种编码器下结果一致，每字符约 0.38 token。

## 面试问答

### Q: Token 和字符有什么区别？

字符（character）是文本的存储单位：一个英文字母、一个汉字、一个空格都算 1 个字符，Python 里 `len(text)` 数的就是它。字符数只跟"写了多少个符号"有关，跟语义无关。

Token 是模型处理文本的计算单位：分词器（tokenizer）把字符串切成模型词表里的条目，模型的一切开销——上下文窗口、计费、生成速度——都按 token 计。

两者不是固定换算关系，具体数字见上面两张实测表（注意编码器）。规律：英文常见单词整个是一个 token，最省；中文按字/词切分，密度最高；代码和 JSON 的标点、缩进会被切碎，居中。

所以"这段文字多少 token"不能只数字符数再乘固定比例，必须用目标模型对应的编码实测（本项目用 `count_tokens(text, encoding_name)`）。

### Q: 上下文窗口限制什么？

上下文窗口是模型一次能"看到"的 token 总数上限。在 OpenAI 的模型上，输入和输出**共享**这个预算：system prompt + 历史对话 + 用户输入 + 模型回复，加起来不能超过窗口大小（如 128K = 131,072 token）。

但要注意，**超出窗口的行为没有通用规则**：有的 API 直接报错（如 context length exceeded），有的拒绝请求，有的按特定策略截断（保留最早/最新的一段、按消息丢弃等），具体表现以所用模型和 API 的文档为准。应用层稳妥的做法是自己预估用量（tiktoken 实测）并在接近上限时主动截断或摘要历史，而不是依赖服务端行为。

窗口还间接限制了：单次回复的最大长度（`max_tokens` 是从同一预算里预留给输出的，不同模型的默认值和上限各不相同）、多轮对话能记住多远、RAG 一次能塞进多少文档。窗口按 token 而非字符计，塞中文比塞英文更快占满窗口。

### Q: 估算一段长文本占 GPT-4o 128K 上下文窗口的百分比

分三步：

1. **确定容量**:128K = 131,072 token。
2. **用对编码**:GPT-4o 用的是 `o200k_base`，不是 `cl100k_base`。本项目 `count_tokens(text, "o200k_base")` 即可。
3. **算出占比**:`占比 = count_tokens(text, "o200k_base") / 131072 × 100%`。

没有现成分词器时的速算（o200k 实测）：英文约 0.18 token/字符，中文约 0.50，代码/JSON 约 0.38。换算成容量直觉：

- 纯英文长文：128K 窗口约容纳 73 万字符；
- 纯中文长文：约容纳 26 万字符；
- 代码/JSON：约容纳 35 万字符。

举例：一篇 5 万字符的纯英文文档 ≈ 5万 × 0.18 ≈ 9,000 token，约占 128K 窗口的 7%；同样 5 万字符的中文文档 ≈ 25,000 token，约占 19%。混合文本按段落类型加权估计，有分词器就直接实测。

## tiktoken 的用途

tiktoken 是 OpenAI 的开源分词器库（BPE 算法），本地运行、无需联网。它能做的是：**对指定编码器，精确统计一段裸文本会被切成多少 token**。典型用途：

1. **费用预估**：API 按 token 计费，且输入 token 和输出 token 单价通常不同（输出更贵）；部分模型还有缓存 token 的折扣计费（重复出现的 prompt 前缀按低价计）。发请求前用 `count_tokens` 算出输入 token 数，可按 `输入 token × 输入单价` 预估下限，实际账单以 API 返回的 usage 字段（prompt_tokens / completion_tokens / 缓存相关字段）为准。

2. **上下文窗口管理**：多轮对话累积前，先算历史消息 + system prompt + 新输入的总 token 数；接近上限时主动截断或摘要最早的消息。要预留 `max_tokens` 给回复。

3. **RAG 文档切块（chunking）**：向量化前按 token 数切分文档（而不是按字符数），保证每块不超嵌入模型的输入上限，也避免句子被从中间切断。

4. **输入超长拦截**：用户粘贴一大段文本时，先测 token 数，超预算就拒绝或提示精简，省一次注定失败的请求。

5. **观察分词行为**：`encoding.encode(text)` 返回 token id 列表，`encoding.decode([id])` 可以反查每个 token 对应的原文片段，用于理解模型"看到"的到底是什么（比如为什么中文比英文费 token）。

**注意事项**：

- 编码必须和模型匹配：GPT-4o / o1 用 `o200k_base`,GPT-4 / GPT-3.5 用 `cl100k_base`，选错结果差很多（中文可差一倍）。
- tiktoken 统计的是**裸文本**。完整聊天请求的实际 token 用量还包括消息角色/格式包装、工具定义（function calling 的 schema）、以及模型端自己的特殊 token 和处理规则，真实数字以 API 响应中的 usage 为准。
- 本项目 `agent_study/token_count.py` 是对 tiktoken 的薄封装：`None` 返回 0；空字符串走 tiktoken 实测（结果为 0）。
