# Optimizer 的职责
根据梯度更新模型参数


## 为什么 Optimizer 接收的是 model.parameters()，而不是整个 model

因为 **Optimizer 的职责被刻意收窄为"只根据梯度更新参数"这一件事**，它需要知道的仅仅是：哪些张量是可训练参数、它们的 `.grad` 是什么。`model.parameters()` 正好提供了这个最小信息集——一个遍历所有 `nn.Parameter` 的迭代器，不多不少。

如果传入整个 model，会带来几个问题：

- **职责混淆**：model 里有 forward 计算逻辑、子模块、buffer（如 BatchNorm 的 running_mean/running_var）等，这些都不该被梯度下降更新。把 model 整个塞给 optimizer，等于让它自己去猜"哪些该更新"。`parameters()` 天然做了筛选——buffer 不是 Parameter，不会被包含。
- **违反单一职责**：model 负责"怎么算"（forward），optimizer 负责"怎么改"（update）。两者通过参数张量解耦后，同一个 optimizer 可以服务任意模型，同一个模型也可以随意换 optimizer（day34 里 SGD 和 Adam 互换就是这么做的）。
- **活引用而非拷贝**：`parameters()` 返回的是张量引用，optimizer 内部保存这些引用，每次 `step()` 都是 in-place 更新同一块内存，model 里的参数随即生效。如果传的是 model，optimizer 还得知道往 model 的哪个属性里写回，耦合太深。
- **参数分组（param groups）**：实际使用中经常要对不同参数设置不同学习率（如"骨干层小 lr、新加层大 lr"），做法是传 `[{'params': model.fc1.parameters(), 'lr': 0.01}, {'params': model.fc2.parameters()}]` 这样的列表。这个 API 以"参数集合"为单位，天然支持分组；以 model 为单位则无法表达。

一句话：optimizer 只依赖"一组带梯度的张量"，这是它和 model 之间最窄、最稳定的契约。

## 解释为什么 Adam 通常更容易训练

Adam 可以概括为 **"带动量的逐参数自适应学习率"**。它为每个参数维护两个滑动平均：

- 一阶矩 m：梯度均值（类似动量，平滑噪声、加速一致方向）
- 二阶矩 v：梯度平方的均值（估计梯度的"尺度"）

更新公式：`Δθ = -lr · m̂ / (√v̂ + ε)`（m̂、v̂ 是偏差修正后的版本）。

它"容易训练"的原因：

1. **每个参数有自己的有效学习率**。梯度大且持续的参数，√v 大、步子自动变小；梯度小或稀疏的参数，相对步子变大。不需要像 SGD 那样反复调一个全局 lr 去迁就所有参数。
2. **对梯度的绝对尺度不敏感**。更新量被 √v 归一化后，量级大约在 lr 附近，不管 loss 放大多少倍，参数每步移动的距离都稳定。特征没归一化、各层梯度尺度差异大（深度网络常见）时也能直接训。
3. **动量平滑了 mini-batch 梯度噪声**，在窄峡谷里不会像裸 SGD 那样来回震荡。
4. **偏差修正**让 m、v 从零初始化开始时前几轮的估计不至于严重偏小，开局更稳。

day34 的实验提供了一个对照视角：**Adam 的优势不是无条件的**。

- `y = 2x + 1`（loss 尺度小）：Adam 100 轮 loss 降到 5.7e-05，远好于 SGD 的 1.3e-03
- `y = 5x - 3`（loss 尺度放大 7 倍）：Adam 反而被 SGD 反超（0.43 vs 0.008），因为自适应步长在简单、良态（well-conditioned）的线性问题上没有便宜可占

经验规律：在**高维、非凸、梯度尺度差异大**的问题（深度网络、Embedding、NLP）上 Adam 几乎总是更省心，所以是 Transformer 的默认选择；在**简单、条件数好**的问题上，调好 lr 的 SGD（尤其带动量）往往收敛更彻底。代价是 Adam 每个参数多存两份状态（m 和 v），显存占用更高。
